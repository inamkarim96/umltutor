Abstract
Modeling is an essential part of software development and software engineering education, but has been difficult for many students to comprehend and use UML notions skillfully. UMLTutor is a smart, web-based learning environment that aims to improve the modeling abilities of students by offering guided practice, automatic feedback, and on-the-spot validation. The system accommodates the development and assessment of various UML diagrams e.g. Use Case Diagrams, Use Case Descriptions, and System Sequence Diagrams (SSDs) in two different modes: Development Mode, and Tutorial Mode. UMLTutor enables students to graphically model their system knowledge and receive instant consistency checks and correction feedback. Teachers enjoy assignment tracking, analytics dashboards, and organised feedback tools. Smart autocompletion, feedback versioning, and performance analytics are also provided, facilitating learning and effective assessment. By integrating natural UI design with automatic UML validation and instant feedback, UMLTutor seeks to close the gap between theoretical knowledge of Modeling and skill learning, thus proving to be a useful utility for both students and teachers in educational institutions.

CHAPTER 1
SOFTWARE PROJECT MANAGEMENT PLAN
1.1 Background
Both Software Engineering and Computer Science students employ the Unified Modeling Language (UML) in understanding, designing and documenting software systems. There are various types of UML diagrams that serve to represent system requirements, structure and behavior.
A number of UML diagrams may be created by students for a particular software system. UML diagrams are inter-related, and any error in one diagram will be reflected in the other. Checking all of these artifacts manually also takes significant time for teachers.
UMLTutor is a web-based learning tool designed for UML education, modeling, automatic verification, and evaluation. It provides a platform for the creation, modification, saving, and submission of UML models by students and classroom management capabilities for the teachers. The system supports five main UML artifacts:
Use Case Diagram
Use Case Description
System Sequence Diagram (SSD)
Class Diagram
Sequence Diagram
It also provides class and assignment management, tutorial support, automated checking, consistency checking across artifacts, assignment submission, teacher evaluation, feedback, notifications, announcements, and reports.
1.2 Problem Statement
It is often challenging for students to create UML diagrams and ensure consistency between them because while every artifact corresponds to a different view of the system, the information provided by these views is related. For instance, there should be an actor or a use case represented both in a Use Case Diagram and the respective Use Case Description and System Sequence Diagram, and Class Diagram information is related to what is depicted in the Sequence Diagram.
Performing these consistency checks manually requires time and does not provide an easy way to give fast and consistent feedback to the student from the instructor. There should be some system which will allow for creating UML diagrams in a consistent environment for students and instructors.
1.3 Proposed Solution
UMLTutor provides a web-based environment for UML modeling, learning, and assessment. Students can create and edit the five UML artifacts listed above, and the system checks their work using predefined rules, including checks for consistency between related artifacts.
Teachers can attach a requirement or case-study description to an assignment; this text is shown to students as the basis for their modeling task. Separately, the checking engine uses text-processing and semantic-comparison techniques parsing, stop-word removal, keyword matching, and synonym/similarity matching to validate the student's own UML work: comparing Use Case Description steps against SSD messages, and SSD messages against Class Diagram operations, to confirm the artifacts are consistent with each other.
1.4 Objectives
For students, the system aims to provide an interactive UML modeling environment covering all five artifacts, help them identify and correct problems through available checking and tutorial guidance, support assignment submission, and allow them to view feedback and checking results.
For teachers, the system aims to support class and assignment management, allow requirement or case-study text to be attached to assignments, reduce the manual effort required to check UML work, and provide automated checking and consistency reports to support evaluation.
1.5 Scope
The scope of UMLTutor covers:
User authentication and role management

Attaching requirement or case-study text to assignments
Automated UML checking and cross-diagram consistency checking

The system is intended for educational use in Software Engineering and Computer Science courses, and focuses on helping students build and improve UML models while reducing the manual effort needed for checking and evaluation.

1.6 Development Approach
UMLTutor was developed using an incremental development approach: the system was built and improved in stages, with each increment adding or improving functionality while earlier functionality was tested and refined. This approach suited a project with several related but separable areas UML editors, assignment management, automated checking, consistency checking, submission, and evaluation.
1.7 Main Users
1.7.1 Student
Students use UMLTutor to view assignments and requirement text, create and edit UML models, request tutorial support, submit assignments, and view checking results, feedback, and reports.
1.7.2 Teacher
Teachers use UMLTutor to manage classes and assignments, provide requirement or case-study information, review student submissions, run or view automated and consistency checking, provide feedback, and support students through tutorial activities.
1.8 High-Level System Workflow
UMLTutor provides two working modes for students: 
Development Mode and Tutorial Mode.
 In Development Mode, students are free to develop the required UML artifacts without being interrupted by the system in every step. Regardless of the chosen mode, students can always run an automatic checking of their work in order to detect rule violation and inconsistencies in the work before its submission. Students can submit their work once done.
Students requiring some guidance during work have the option of Tutorial Mode. A student needs to make a request to use Tutorial Mode on the work he/she intends to submit, and a teacher needs to approve the request in order for step-by-step guidance to be available. If approved, the system will guide the student through the tasks one after another, check the completed step, correct it if necessary and then let him/her proceed.
Once a student has submitted his/her work, the teacher can launch the checking engine and run it against the UML artifacts submitted. The system will generate a report on the consistency, which the teacher uses together with the work to check the student's work. After reviewing the work, the corresponding report is provided to the student.
1.9 Role of Semantic Consistency Checking
An assignment may include requirement or case-study text that is shown to students as the basis for their modeling task. UMLTutor's checking engine uses text-processing and semantic-matching techniques parsing, stop-word removal, and synonym/similarity comparison to confirm that a student's UML artifacts are consistent with one another: matching Use Case Description steps to the corresponding SSD messages, and SSD messages to Class Diagram operations. This semantic matching between a student's own artifacts, rather than free-text parsing of the requirement or case-study description, is what supports the automated and consistency checking described in the next section.
1.10 Automated Checking and Consistency Checking
Automated checking applies predefined rules to a student's UML work to identify problems in an individual model, for example checking whether required elements or relationships follow the defined rules. Consistency checking compares related information between artifacts for example, comparing a Use Case Diagram with its Use Case Description and System Sequence Diagram, or a Class Diagram with a related Sequence Diagram to identify differences or conflicts between related UML artifacts. A consistency report can be generated both while a student is working, through in-editor checking, and by the teacher running the checking engine against the submitted work.

1.12 Related Work
Several existing tools support UML modeling or software-engineering education, and it is useful to place UMLTutor in that context. Provide refences to the software listed in the sections beow
General-purpose UML modeling tools such as diagrams.net, Lucidchart, and StarUML provide diagram creation and modeling features, but they are not designed specifically around UML classroom assignments, student submissions, and the cross-diagram checking workflow provided by UMLTutor.
Learning-management systems (for example, Moodle or Google Classroom) support assignment distribution and submission, but have no built-in understanding of UML and cannot check a UML diagram’s structure or its consistency with other diagrams.
Automated code and static-analysis tools (linters, style checkers) apply a similar idea — rule-based automated checking  to source code rather than to UML diagrams, and do not address modeling education.
UMLTutor is positioned differently from these tools: it combines a purpose-built UML editor, an assignment/classroom workflow, and a rule-based checking engine that also checks semantic consistency between a student’s own related diagrams of the same system. This combination — modeling, classroom management, and automated cross-diagram checking in one system — is the specific gap UMLTutor is intended to fill.
1.13 Summary
UMLTutor is an online tutoring system for the purpose of Software Engineering and Computer Science education. It offers a common ground for UML modeling, learning, verification, consistency verification, assignment submission, and teacher evaluation in five types of UML artifacts, including Use Case Diagram, Use Case Description, System Sequence Diagram, Class Diagram, and Sequence Diagram. The cross-artifact consistency is provided by means of text processing and semantic matching in the verification process, and not as a standalone module for the user. 2.1 Introduction
2.1.1 Purpose
This Software Requirements Specification (SRS) defines the functional and non-functional requirements of UMLTutor. It explains what the system provides to students and teachers and provides the basis for the design, implementation, and testing described in the following chapters.
2.1.2 Scope
UMLTutor is a web-based educational system for Software Engineering and Computer Science education. This enables the students to design, edit, save and interact with five UML diagrams: Use Case Diagram, Use Case Description, System Sequence Diagram (SSD), Class Diagram, and Sequence Diagram. The system offers assignment-based modeling, possible text of requirements or case study, validation of diagrams, tutorial help, submission and review by the teachers.
Teachers may attach optional requirement or case-study text to an assignment for students to read; the checking process itself relies on text-processing and semantic-matching techniques applied between a student's own UML artifacts, rather than on parsing the attached text.
2.1.3 Objectives
For students, the system shall provide an interactive modeling environment across all five UML artifacts, support free modeling in Development Mode, provide step-by-step guidance in Tutorial Mode, allow students to submit completed assignments, and allow them to view available checking results and feedback.
For teachers, the system shall support class and assignment management, allow requirement or case-study information to be provided with assignments, allow submitted work to be checked, and support review of checking results, consistency reports, and student submissions.
2.2 Overall Description
2.2.1 Product Perspective
UMLTutor is a web-based educational application combining UML modeling, learning, automated checking, consistency checking, assignment management, submission, and evaluation. The frontend provides the interface through which students and teachers work with UML editors, assignments, classes, tutorial support, submissions, checking results, and reports. Backend services handle application logic, checking operations, and communication with the database.
2.2.2 Product Functions
User authentication and role-based access.
Class and assignment management.
Creation, editing, saving, and submission of all five UML artifacts.
Development Mode for free UML modeling.
Tutorial Mode for guided, step-by-step modeling and correction.
Semantic consistency matching between related UML artifacts to support checking.
Automated UML checking using predefined validation rules.
Cross-diagram consistency checking between related UML artifacts.
Teacher review of submitted assignments and checking results.
Feedback and report viewing.
2.2.3 User Characteristics
Students are expected to have basic knowledge of Software Engineering and UML. They use UMLTutor to view assignments, create UML models, work in Development Mode or Tutorial Mode, submit assignments, and review available results and feedback.
Teachers are expected to have knowledge of UML and Software Engineering. They use UMLTutor to manage classes and assignments, provide requirement or case-study information, review student submissions, run the checking process, and review checking and consistency results.
2.2.4 Constraints
The system is accessed through a web interface over HTTP/HTTPS.
Users must authenticate before accessing protected features, and access depends on the user's role.
Automated checking depends on the information available in the submitted UML artifacts.
Requirement and case-study processing depends on the quality and clarity of the provided text.
The application requires its backend and database services to be running for normal operation.
2.3 Specific Requirements
2.3.1 External Interfaces
The system provides a web-based user interface for students and teachers. Students interact with UML editors, assignments, tutorial activities, submissions, and available results. Teachers interact with classes, assignments, submitted work, checking functions, reports, and feedback.
The frontend communicates with backend services through application APIs. Authentication and protected operations are handled according to the user's role.
2.3.2 Performance Requirements

UML editing operations should provide a responsive interface during normal use.

The system shall authenticate users before allowing access to protected functions.

3.7 Authentication and Authorization Design
UMLTutor uses Firebase Authentication: the frontend uses the Firebase client SDK to sign a user in, the backend uses the Firebase Admin SDK to verify the resulting ID token on each API request, and the authenticated user is then looked up in PostgreSQL to determine their role. Role-based authorization then controls access
 for example, student routes require the STUDENT role, while teacher management and review routes require the TEACHER role.
3.8 Requirement Processing and Automated Checking Design
3.8.1 Semantic Consistency Checking
UMLTutor's checking engine does not parse an assignment's attached requirement or case-study text into a separate model. Instead, semantic matching is applied between a student's own UML artifacts, so that related information stays consistent as it moves from one diagram to another.
The backend's nlp/ folder (semanticService, sentenceUtils, similarity, and constants) provides this support: parsing a Use Case Description step or an SSD message into its component parts, normalizing and comparing terms (evaluateFunctionMatch, fuzzyMatch, normalizeName), and comparing method signatures between an SSD message and a Class Diagram operation (compareParameterLists, compareClassOperation). This is what allows the checking engine to confirm, for example, that a step written in a Use Case Description is reflected by a matching message in the corresponding SSD, and that an SSD message corresponds to an operation defined on the right class. The requirement or case-study text a teacher attaches to an assignment is stored and shown to students as context for their modeling task, but it is not itself parsed by the checking engine.
3.8.2 Validation Rule System
The backend uses a centralized rule registry as well as a rule pipeline that takes into consideration the dependencies among the rules. There are 124 rules in the registry currently, out of which 117 are active and classified according to the area of UML and the type of checking they do (structural, consistency, naming, completeness, UML standards, and best practices).
The pipeline makes use of the dependency knowledge about the rules to ensure that the absence of some required element does not create a bunch of errors unrelated to the actual problem; the steps followed in this process are the loading of rules, resolving of their dependencies, running of required rules, identifying the root cause, suppressing the unnecessary errors, and finally generating the results.
3.8.3 Six-Phase Checking Pipeline
Checking is organised into six phases, run in order:
Use Case Diagram: system boundary, actor and use case presence and naming, connectivity, relationships, and duplicates;
Use Case Description: primary actor, pre/postconditions, main flow, alternative flows, and orphan/duplicate descriptions;
System Sequence Diagram: SSD completeness, actor/system lifelines, message direction and structure, and semantic alignment with the description;
Class Diagram: class structure, relationships, methods, attributes, and SSD-operation compatibility;
Sequence Diagram:  lifelines, messages, call/return structure, activations, and class-operation relationships;
Cross-Diagram Consistency: checking relationships across all five artifacts together, which is central to UMLTutor's purpose of keeping different UML views of the same system consistent.
3.8.4 Cross-Artifact Semantic Matching
Within the phases above, the checking engine performs targeted semantic comparisons between related artifacts rather than checking each diagram only in isolation: Use Case Description steps are matched against the corresponding SSD's messages (validateDescriptionSSDSemantics), and SSD messages are matched against the operations defined on the relevant class in the Class Diagram (validateSSDClassOperations). Matching uses fuzzy/synonym comparison rather than requiring an exact wording match, since students commonly phrase the same step or operation slightly differently across artifacts.
3.8.5 Suggestion Engine
After checking, UMLTutor's suggestionEngine generates suggestions for detected issues from the identified rule code, producing a suggested improvement shown to the student or teacher to help explain how the UML model can be corrected.

Figure 3.4 – UMLTutor Relational Database Design (ERD)

User represents a student or a teacher: if the User is a teacher then he manages Classes and evaluates the students’ submissions (Evaluation). 3.13 Caching, Security, and Performance Design
The in-memory caching is used in the backend part of the application; additionally, Redis can be used as an optional shared cache, and in case Redis is not available then the application will continue to work with the in-memory cache. API security consists of Firebase token verification, role-based authorization, Helmet, CORS, rate-limiting, request validation and centralized error handling. The performance-oriented features include database indexes, request/user caching, Firebase token caching, database connection keep-alive, logging of requests processing time and response compression.
3.14 Error Handling and API Response Design
On the backend there is one centralized error-handling middleware so that errors from any layer (validation, authentication, database, or checking) are converted into a consistent json response shape, instead of each route handling errors differently. A typical error response contains a success flag, an error code or category, a human-readable message, and, for validation errors, details identifying which field failed and why. This enables the frontend to show user friendly messages (i.e. "assignment requirement text is required" instead of a generic failure) and maintains consistent logging via Winston throughout the entire backend.
3.15 Deployment Architecture
The project contains docker configuration for both frontend and backend and Kubernetes manifests (k8s-full-stack.yaml) for a full-stack deployment. This allows us to build the application as container images and deploy them consistently across different environments (local development, staging, or production) where the frontend, backend, and PostgreSQL database can all run as individual services. The environment-specific configuration (database connection string, Firebase credentials, Redis and Cloudinary settings) is passed through environment variables instead of hard-coded so the same container images can be reused across environments.
3.16 Design Principles
Separation of responsibilities frontend, backend, database, checking logic, and supporting services each have a distinct role.
Reusable checking rules are maintained in one central rule registry.
Dependency-aware validation rule dependencies reduce unnecessary cascading errors.
Role-based access student and teacher’s and abilities are kept separate by role.
Semantic consistency checking the system compares a student's own artifacts against one another rather than relying on a single fixed case study or free-text parsing.
Educational feedback checking results and suggestions are designed to help students improve, not only to flag mistakes.

In this chapter we presented the design of the current implementation of UMLTutor, consisting of a React frontend, a Node.js/Express backend and a PostgreSQL database accessed by Prisma. The checking system is one of the central parts of the design, built on top of a 124-rule registry (117 enabled) and a six-phase, dependency-aware pipeline, along with the semantic consistency matching (nlp/ modules) that supports it. The database holds users, classes, assignments, submissions, the five types of UML artifacts, evaluations, notifications, announcements, resources and submission exports. 4.5 Checking Engine Implementation
The checking engine described in Section 3.8 is implemented as a static class, CheckingEngine, in services/checkingEngine.js. Its checkModel(model, section, targetId) entry point is called from CheckingController for both the student-facing live check (POST /api/check) and the teacher-facing post-submission check (POST /api/submissions/:id/run-check).
The 124 rules in rules/ruleRegistry.js are grouped by UML area and category, and executed by rules/rulePipeline.js, which resolves declared dependencies between rules before running them so that a root-cause problem is reported once rather than triggering a cascade of dependent errors. Where a rule's check requires comparing two related artifacts — for example, a Use Case Description step against an SSD message, or an SSD message against a Class Diagram operation — the checking engine delegates to ssdValidationService for structural checks and to the nlp/ module (semanticService.js) for semantic term comparison (evaluateFunctionMatch, fuzzyMatch, normalizeName, compareParameterLists, compareClassOperation).
After the rule pipeline completes, suggestionEngine.js turns the resulting rule violations into a suggestion and a score that are returned to the caller and, for a teacher-run check, persisted onto the Evaluation record.

5.1 Introduction
This chapter describes the testing approach for UMLTutor. Testing verifies that the implemented system works according to the requirements in Chapter 2 and the design in Chapter 3, and covers not just whether pages open correctly but also data saving, API communication, UML model validation, checking rules, consistency between artifacts, user roles, and assignment submission. The main testing activities are functional testing, API testing, unit testing, integration testing, UML/consistency checking tests, authentication and authorization testing, database-related testing, and user interface testing. Actual results should be recorded in the test logs in Appendix A.
5.2 Test Approach
5.2.1 Unit and Integration Testing
Unit testing checks small parts of the system in isolation  validation functions, requirement parsing functions, checking rules, utility functions, suggestion generation, and service functions — to find errors before testing the whole application. The backend’s automated Jest test suite currently contains 29 test suites and 304 tests. Integration testing then checks that parts work correctly together: frontend/backend communication, backend/database communication, authentication with protected APIs, assignment and submission operations, and the requirement-processing-to-checking-engine pipeline. For example, saving a Use Case Description should update the interface and also reach the backend and be stored correctly in PostgreSQL.
5.2.2 API, Functional, and Security Testing
API testing checks request format, authentication, authorization, input validation, and both successful and error responses; the backend also documents its API through Swagger, and API testing can be performed with Postman or a similar client. Functional testing checks whether the system performs the functions from Chapter 2 login, creating/saving/editing UML artifacts, checking, submission, teacher review, feedback, and reports. Security testing checks that users can access only the functions allowed for their role: valid and invalid logins, token validation, student and teacher access control, and rejection of unauthorized API requests.
5.2.3 UML Checking Testing
The checking engine is a major part of UMLTutor, currently containing 124 registered rules (117 enabled) across six checking phases. Testing therefore covers both individual rules and the complete checking flow, for each of the six areas: Use Case Diagram, Use Case Description, System Sequence Diagram, Class Diagram, Sequence Diagram, and Cross-Diagram Consistency. Both positive tests (a correct model should not produce incorrect errors) and negative tests (a deliberately incorrect model should produce the expected result) are used, and testing checks correct rule selection, rule dependencies, error codes, severity, suggestions, and cross-artifact semantic matching not just whether the engine runs, but whether its output matches the expected result.

5.10 Checking Engine Test Coverage
Because the checking engine contains a large number of validation rules, its testing needs to cover more than whether the engine runs without crashing. Testing is split into two complementary categories:
Positive tests a correct UML model should not produce incorrect errors. This guards against over-eager rules that would frustrate students who have modelled something correctly.
Negative tests a deliberately incorrect UML model should produce the expected checking result, with the correct rule code, severity, and (where applicable) suggestion.
Beyond individual rules, checking-engine testing also covers correct rule selection for a given diagram type, rule dependency behaviour (so a root problem does not generate a flood of secondary errors), the accuracy of generated suggestions, and cross-diagram semantic consistency checks. A test that only confirms the engine executed without error is not sufficient  the output must also match the expected result for that specific input.
5.11 Regression Testing and Test Environment
Regression testing is run after important changes to the code, and is especially important for UMLTutor because a change to a shared checking rule can affect several checking areas at once (e.g. Use Case Diagram, Description, SSD, Class Diagram, Sequence Diagram, and Cross-Diagram checking together). Previously-passed tests should therefore be re-run after changes to the checking engine. The test environment mirrors the production architecture from Chapter 3: browser, React frontend, Node.js/Express backend (with Firebase Authentication, the checking engine, and requirement/NLP processing), Prisma ORM, and PostgreSQL  all required services should be running before integration tests are performed.

CHAPTER 6
CONCLUSION AND FUTURE WORK
6.1 Conclusion
UMLTutor is a web-based learning and assessment system built to help students learn UML modeling and improve their understanding through practical work. It gives students a structured environment to create UML models, receive automated feedback, correct their work, and submit assignments for teacher review, across five UML artifacts: Use Case Diagram, Use Case Description, System Sequence Diagram, Class Diagram, and Sequence Diagram. These are not treated as separate diagrams  UMLTutor also checks the relationships and consistency between them, which helps surface problems that would not be visible when each diagram is checked on its own.
The system is built with React on the frontend and Node.js/Express on the backend, with PostgreSQL (via Prisma ORM) for persistent storage and Firebase Authentication for sign-in and role-based access. Its automated checking engine, one of the project’s central components, currently implements 124 validation rules (117 enabled) across six checking phases the five individual artifact types plus cross-diagram consistency  and uses rule dependencies to avoid reporting many secondary errors caused by the same root problem. Semantic matching between a student's own related artifacts is supported with the help of NLP techniques (text normalization, similarity checking, and semantic comparison) as a supporting part of that checking pipeline, not as a separate feature. The system also provides tutorial support so students can practice with guidance, and lets teachers review submissions, check results, give feedback, and record evaluations.
The project set out to achieve several objectives, each substantially met by the current implementation: providing an interactive, multi-artifact UML learning environment; automated checking that identifies problems in individual and cross-diagram work; feedback and suggestions that help students correct their own mistakes; semantic consistency checking that connects a student’s own related artifacts to one another; and tools that let teachers manage classes and assignments, review work, and provide evaluation with less manual effort than checking every diagram by hand.
6.2 Main Contributions
Multiple UML artifacts in one system rather than focusing on a single diagram type, UMLTutor supports five, giving a more complete view of a student’s modeling work.
Automated checking at scale a 124-rule registry reduces the manual effort needed to find common UML problems and returns structured results instead of requiring a teacher to find every issue by hand.
Cross-diagram consistency checking the system can catch cases where individually valid diagrams do not describe the same system consistently, which is easy for a human reviewer to miss.
Semantic consistency support comparing a student's own related artifacts to one another surfaces inconsistencies that would be hard to notice by reading each diagram separately.
Learning-oriented feedback tutorial functionality and generated suggestions are designed to help students understand and correct problems, not just to flag them.
6.3 Limitations
Although UMLTutor provides a complete set of core functions, some limitations remain in the current version.
UML modeling scope the editors support the UML elements and relationships implemented so far; UML has many advanced constructs that are not all covered yet.
Automated checking limitations a rule can only catch a problem that its logic covers; some complex modeling decisions still require human judgement and cannot always be decided correctly by fixed rules.
NLP limitations natural language is ambiguous, and different students may describe the same requirement using different wording, so text processing will not always extract the exact intended meaning.
Dependence on artifact quality semantic consistency checking depends on how clearly a student names and describes elements across artifacts; inconsistent naming can reduce match accuracy.
Service dependency as a web application, UMLTutor depends on its backend, database, authentication, and other configured services being available; a problem in one of these can affect the user experience.
6.4 Future Work
The current system covers the main functionality needed for UML learning and automated checking. Several areas are natural candidates for future versions, grouped below by theme.
6.4.1 Checking and Modeling Depth
Future versions could support more UML elements and relationships, extend the rule registry to cover more advanced modeling cases, and move beyond structural validation toward deeper semantic checking  for example, better judging whether a use case actually matches its description, whether SSD messages correctly represent the main flow, whether Sequence Diagram messages match class operations, or whether different artifacts describe the same underlying business requirement.
6.4.2 Requirement Processing and Feedback
The requirement/case-study pipeline could be improved with better entity extraction, actor and use-case identification, semantic similarity, handling of different sentence structures and synonyms, and requirement-to-UML mapping, so the system stays reliable when students phrase the same idea differently. Student feedback could also become more specific explaining why a problem matters, showing an example of a correct structure, and linking a suggestion back to the relevant requirement or UML artifact rather than only reporting that an error exists.
6.4.3 Learning and Teaching Support
The tutorial system could be expanded with graded practice exercises (beginner to advanced), step-by-step diagram creation, and progress tracking, allowing students to use UMLTutor for regular practice as well as assignments; performance data could support more personalised recommendations when a student repeatedly makes the same kind of mistake. Teacher dashboards could be extended with analytics such as common errors, most frequently failed rules, class-level performance trends, and frequently requested tutorial topics, helping teachers identify where a class needs more instruction.
6.4.4 Collaboration, History, and Reporting
A future version could support real-time collaborative modeling a shared canvas, live updates, presence, comments, and version history useful for group assignments, and could keep a version history of a student’s work so students and teachers can compare an original diagram, a corrected diagram, and the final submission. Reports could be extended to combine assignment requirements, diagrams, checking results, consistency issues, corrections, feedback, and final evaluation into a single, more complete record of a student’s work.
6.4.5 Performance, Deployment, and Scale
As the number of users, assignments, and checking rules grows, future work could focus on database query optimisation, improved caching, background checking jobs for large submissions, faster rule execution, and better frontend loading performance, alongside deployment improvements such as containerised or cloud deployment, horizontal and database scaling, centralised logging and monitoring, and automated deployment pipelines making the system easier to run at the scale of a full university course or department.
6.5 Lessons Learned
Several practical lessons emerged during the development of UMLTutor. Building consistent validation across five related UML artifacts required careful thought about how diagrams reference each other (through relatedId links) so that a change in one artifact could be checked against the others; this relationship-first thinking shaped much of the later checking-engine design. Processing free-text requirements also proved harder than expected — real requirement text is written in many different styles, so confidence-based matching (rather than treating every requirement sentence as a strict UML element) turned out to be necessary to avoid generating unhelpful or misleading requirements from unclear text. Finally, a dependency-aware checking pipeline was needed once the rule count grew past roughly one hundred rules, since a single missing element could otherwise trigger many secondary errors that obscured the actual root cause for the student.
6.6 Final Conclusion
UMLTutor provides a practical solution for learning and assessing UML modeling in a single web-based environment, combining UML editors, requirement processing, automated checking, cross-diagram consistency checking, tutorial support, assignment submission, and teacher evaluation. Its most distinctive part is the connection it draws between different UML artifacts: rather than checking every diagram in isolation, it also considers how those diagrams describe the same system together. NLP supports this by helping the system understand and use requirement and case-study text, as a supporting technology inside the checking workflow rather than a separate main feature.
The project demonstrates how ideas from software engineering, databases, web development, UML, automated validation, and text processing can come together in one practical educational system. Future development more UML rules, stronger semantic checking, improved NLP processing, personalised learning, richer analytics, collaborative modeling, and better scalability can build on this foundation toward a larger UML learning and assessment platform.
